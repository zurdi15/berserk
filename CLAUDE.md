# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

berserk — self-hosted workout tracker. FastAPI + SQLAlchemy/Alembic on SQLite (backend), Vue 3 + TypeScript + Tailwind 4 + Pinia (frontend), a Capacitor Android WebView shell (mobile/), all shipped as a single non-root Docker image where FastAPI serves the built SPA as static files.

**Language convention:** code comments, commit messages, and the CHANGELOG are written in Spanish. Comments are "why-comments" — they explain rationale and history, not what the code does; keep that style. The UI is bilingual (es/en, `es` fallback): every user-facing string must exist in both `frontend/src/i18n/es.ts` and `en.ts`.

## Commands

```bash
./dev.sh              # backend :8000 + frontend :5173 (hot reload); use the app at :5173
./dev.sh back|front   # only one side
./dev.sh --seed       # seed synthetic dev data first (idempotent)
```

Dev data lives in `./data` (gitignored, override with `BK_DATA_DIR`). API docs at `http://localhost:8000/api/docs`. Vite proxies `/api` → `:8000`.

Backend (from `backend/`, uses [uv](https://docs.astral.sh/uv/)):

```bash
uv sync                                   # install deps
uv run pytest                             # all tests
uv run pytest tests/test_workouts_api.py -k test_name   # single test
BK_DATA_DIR=../data uv run alembic upgrade head         # apply migrations
BK_DATA_DIR=../data uv run alembic check                # models.py vs migrations drift (CI-gated)
uv run alembic revision --autogenerate -m 'descripcion' # new migration after editing models.py
```

Frontend (from `frontend/`, Node 22+):

```bash
npm run test                     # vitest (happy-dom, TZ pinned to Europe/Madrid)
npx vitest run src/lib/__tests__/foo.spec.ts   # single test file
npm run build                    # guard:tokens + vue-tsc --noEmit + vite build
npm run build:tokens             # regenerate src/styles/tokens.css from src/tokens/index.ts
npm run guard:utilities          # verify Tailwind utilities actually emitted CSS (needs dist/)
```

CI (`.github/workflows/ci.yml`) runs: backend `alembic upgrade head` + `alembic check` + pytest; frontend `build:tokens` + `git diff --exit-code src/styles/tokens.css` (the generated file is committed — regenerate and commit it when tokens change), `guard:tokens`, tests, build, `guard:utilities`; then a Docker build.

## Architecture

### Backend (`backend/app/`)

- `main.py` `create_app()` wires everything; `asgi.py` is the uvicorn entrypoint. Routers (`routers/`, one per resource) → services (`services/`, the nontrivial domain logic: workouts, sets, progress, calendar, backup, images) → `models.py` (single file, all SQLAlchemy models). Pydantic request/response models in `schemas/`.
- Config is `pydantic-settings` with env prefix `BK_` (`config.py`), cached with `lru_cache` — tests must set env vars **before** importing the app (see `tests/conftest.py`, which also sets `BK_BCRYPT_ROUNDS=4`).
- SQLite with WAL + foreign keys enforced via connect-event pragmas (`db.py`). Schema changes always go through an Alembic autogenerated revision; `dev.sh` warns and CI fails on drift.
- Auth: session cookie `bk_session`, invite-only signup — the first account bootstrapped becomes admin, later accounts come from single-use admin-issued invite links. Admins can act as another user via a request header resolved in `get_current_user` (see `test_act_as.py`). Multi-user read sharing lets one account grant another read access.
- The global exercise catalog is seeded idempotently at startup (`seed.py`); `dev_seed.py` is dev-only synthetic history, never imported by the runtime.
- Backup export/restore takes a non-blocking `threading.Lock` (409 if busy) and restores atomically with a fallback.
- `BK_SERVE_STATIC=0` in dev so `:8000` doesn't serve a stale compiled SPA.

### Frontend (`frontend/src/`)

- `api/client.ts` is the single fetch wrapper: `ApiError` carries a backend error slug (i18n keys under `errors.*`), `OfflineError` distinguishes network death from HTTP errors, and it injects the act-as header.
- **Offline (gym mode):** workout mutations made without network are queued FIFO in localStorage (`offline/outbox.ts`) and replayed in order on reconnect. Offline-created entities use negative temp ids mapped to real ids during replay; each entry has a `client_id` UUID the backend uses for dedupe. Read caching in `offline/readCache.ts`. PWA precaches the shell only — the API is never cached by the service worker.
- **Design system:** `lib/Bk*.vue` primitives; `views/` per route; feature components under `components/<area>/`. Design tokens live in `src/tokens/index.ts` (single source of truth) and are compiled to `src/styles/tokens.css` — never hand-edit colors/durations/easings. `guard-tokens.sh` fails the build on raw hex, raw `cubic-bezier(`, or Tailwind arbitrary values (`[13px]`) anywhere outside the tokens source.
- **No native form controls:** `<select>` and `<input type="date|time">` are banned (they open OS pickers on Android); use `BkSelect`/`BkDateField`/`BkTimeField`. Enforced by `src/__tests__/noNativeFormControls.spec.ts`.
- Tailwind 4 silently drops unknown utilities — `guard:utilities` greps `dist/` to confirm every color utility used in `src/` really generated CSS. If it flags a false positive (e.g. an SVG attribute), add it to the whitelist individually, never by prefix.

### Mobile (`mobile/`)

Thin Capacitor Android shell: a WebView pointed at the production server URL in `capacitor.config.json` (no bundled frontend). Built and signed per release tag by `.github/workflows/android.yml`.

## Releases and deployment

**Every feature ships end to end** — it is not done when the code is merged, it is done when the new version runs in the cluster and the user has been told. The six steps, in order:

1. **Release commit.** Version `0.x.y` is kept in sync across `backend/pyproject.toml` (+`uv.lock`), `frontend/package.json` (+lock), and `mobile/package.json` (+lock). A release is a `chore: release vX.Y.Z` commit bumping all of them plus a Spanish CHANGELOG entry (sections: Añadido/Cambiado/Arreglado/Eliminado, written for end users). Feature work goes in its own commit(s) before it; releases land straight on `main` (no PR — see the git history).
2. **Push and tag.** `git push origin main`, then a `v*` tag pushed separately. The tag triggers `release.yml` (multi-arch Docker image → `ghcr.io/zurdi15/berserk:X.Y.Z` + `:latest`) and `android.yml` (signed APK). Wait for the image to actually exist before step 4 — ArgoCD will happily try to pull a tag that is not published yet.
3. **Create the GitHub Release** — nothing automates this, and `android.yml` *needs* it: its last step polls for the Release for 10 minutes and then fails the run, so the APK builds fine and is thrown away. Title is the bare tag, body is that version's CHANGELOG section with the `## X.Y.Z - date` heading stripped:

   ```bash
   awk '/^## X\.Y\.Z/{f=1;next} /^## /{f=0} f' CHANGELOG.md > /tmp/notes.md
   gh release create vX.Y.Z --title vX.Y.Z --notes-file /tmp/notes.md --latest
   ```

   If the APK run already failed for this reason, create the Release and re-dispatch it against the tag — that is what the `workflow_dispatch` input exists for: `gh workflow run android.yml --ref vX.Y.Z -f tag=vX.Y.Z`. Confirm the `berserk-vX.Y.Z.apk` asset actually landed on the Release afterwards.
4. **Bump the service in ginnugagap.** The homelab is a single-node K3s cluster driven by ArgoCD GitOps from the `zurdi15/ginnugagap` repo (`master`, auto-sync + self-heal). Berserk's manifests live in `k8s/apps/berserk/`; the deploy is one line — `image:` in `deployment.yaml`. Work on the server checkout over SSH (host `ginnugagap`, user `ymir`, key `~/.ssh/ginnugagap`):

   ```bash
   ssh ginnugagap 'cd ~/valhalla/ginnugagap \
     && sed -i "s|berserk:.*|berserk:X.Y.Z|" k8s/apps/berserk/deployment.yaml \
     && git commit -am "berserk: X.Y.Z" && git push'
   ```

   The commit message convention in that repo is bare `berserk: X.Y.Z` (not Conventional Commits — match the neighbours).
5. **Force the ArgoCD refresh, then confirm it rolled out.** Do not wait on auto-sync: push the refresh so ArgoCD re-reads the repo now. The `argocd` binary is **not** installed on the host — this homelab drives it by annotating the `Application` (the same thing the Telegram bot's `/argocd` hard-refresh button does). The `Application` objects live in the `argocd` namespace, while the workloads live in `apps`:

   ```bash
   ssh ginnugagap 'kubectl -n argocd annotate application berserk argocd.argoproj.io/refresh=hard --overwrite'
   ```

   Then verify, rather than assuming: the `Application` should report `Synced`/`Healthy` at the revision you just pushed, and the pod should be `Running` on the new image.

   ```bash
   ssh ginnugagap 'kubectl -n argocd get application berserk \
       -o jsonpath="{.status.sync.status} {.status.health.status} {.status.sync.revision}"; \
     kubectl -n apps get pods -l app=berserk'
   ```

   For a real end-to-end check, the version is baked into the served bundle — pull the `/assets/index-*.js` referenced by `https://berserk.ginnugagap.net/` and grep it for `X.Y.Z`. A tag that fails to pull leaves the old pod serving happily, so silence is not success.
6. **Notify over Telegram.** Use the `telegram-notify` skill, which lives in the ginnugagap repo (`telegram_bot/claude-skill/SKILL.md`, symlinked into `~/.claude/skills/` **on the server**, not on the dev machine). From here it is reachable over SSH by absolute path — the wrapper is not on `PATH` in a non-interactive shell:

   ```bash
   ssh ginnugagap '~/valhalla/ginnugagap/telegram_bot/notify.py -s ok -p berserk \
     -t "berserk vX.Y.Z en el cluster" "<qué trae la versión, en español>"'
   ```

   Pass `-p berserk` or the context line reports the server's cwd instead of the project. One message per release, in Spanish, once the version is really live. Read that SKILL.md for the flags and the message rules before writing the first one.
